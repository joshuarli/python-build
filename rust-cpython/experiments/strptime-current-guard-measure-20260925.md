# Current numeric `datetime.strptime` guard measurement

**Verdict: promising bounded diagnostic; keep the optional experiment, but do not promote a quiet-host speed claim from this run.** The exact current `0007-rust-strptime-numeric.patch` parser hunk and standalone private C/Rust extension were measured against pure pinned `_strptime.py` on the same accepted, read-only CPython 3.16 executable. Five serial, counterbalanced complete log-ingest pairs gave a median guarded/pure wall ratio of **0.756** and kernel user-plus-system CPU ratio of **0.745**. The host load rose from 3.75 to 5.77 during this short run. These observations replace the pre-revision ratios for this source; they do not establish performance on a quiet host.

The pure parser came from pinned Rust-for-CPython commit `b812b4a7b9efaca46b98544a8633b7d7e454166b` and matched the accepted installed parser byte for byte (SHA-256 `1cab861d2e3ba6cb778f2ce8ef921ae82d7dbfd3dc7fb049945e5fc51ca55ddb`). The current patch SHA-256 was `c9a65f805292b6ae495c7e211e758d20fb12ad59a9db14699f372c67b6d20326`; the exact patched parser hash was `b939f0602fe8df9b325891f92465cdd8c8913b57fe92473b182e720eacf6f2a7`. Both arms used accepted executable SHA-256 `6eeeb64b9eb161d4d5edb9200e79146dabd8acc0f73fcdca48417d0e3c9531bd`. The standalone extension from the patch's exact `module.c` and `scan.rs` new-file hunks had SHA-256 `63b3c447a92d57a7c3e59178b9f21dc0da117047abb72d5dd293721cd7aa9917`. The [compact data](data/strptime-current-guard-measure-20260925.json) records every source and compiler hash, direct compiler argument vector, compiler resource result, and attempt.

The workload was `strptime_numeric_workload.py --count 30000 --rounds 2`: each fresh process made 60,000 public `datetime.datetime.strptime` calls. Every completed attempt returned the same complete output, including digest `bb2b012282c2f8f0bad78f553fe946f3f093c96bfb8eca6a5077b5ee2e1a9473`. Both sides used `-S -B`, `PYTHONDONTWRITEBYTECODE=1`, an initially empty `PYTHONPYCACHEPREFIX`, and source overlays selected by `PYTHONPATH`. Import probes observed each exact overlay path, observed the private extension only in the guarded arm after two eligible calls, and found no cached bytecode. No `.pyc` appeared during measurement.

Two pure/pure pairs gave wall ratios 0.992–1.007 and CPU ratios 0.991–0.999. The five guarded/pure wall ratios were 0.776, 0.722, 0.742, 0.756, and 0.758; CPU ratios were 0.757, 0.734, 0.745, 0.744, and 0.745. Median complete-process wall times were 0.336 s pure and 0.253 s guarded per 60,000 records, or 5.59 and 4.22 microseconds per record. Median kernel CPU was 0.323 s pure and 0.241 s guarded, or 5.39 and 4.02 microseconds per record. Direct `os.wait4` accounted each workload's user and system CPU, peak RSS, and swaps; this workload spawned no children.

A separate three-pair `/usr/bin/time -l -p` pass measured guarded minus pure peak RSS as +81,920, +262,144, and +262,144 bytes, and physical footprint as +65,560, +229,376, and +229,376 bytes. Every workload and compiler attempt reported zero process swaps; host swap remained at 243.88 MiB. Direct compiler steps took 0.066 s wall and 0.055 s CPU for Rust (`99,483,648` bytes peak RSS), then 0.234 s wall and 0.193 s CPU for clang (`53,231,616` bytes peak RSS). The clang driver may invoke a short-lived linker child, so its direct `wait4` CPU and RSS are not a complete compiler process-tree total.

The first import probe failed because this interpreter's `_strptime` module did not expose `__cached__`; the corrected probe treats that attribute as optional. The failed attempt, its error, and the successful continuation have distinct IDs in the JSON. This run used no full interpreter rebuild, PGO job, test suite, formatter, or linter. It is one loaded-host diagnostic, with no broader variance or multi-host qualification.
