# Exact TAR checksum scan, 2026-09-25

**Recommendation: keep the narrow scanner as a promising experiment.** Five serial, alternating-order control/candidate pairs of complete public `tarfile` reads reduced median full-process wall time by **10.18%** and kernel user plus system CPU by **10.38%**. All five pairs favored the candidate. Five preceding control/control pairs bounded local wall variation at −0.50% to +3.79% (the high first pair; the other four were within ±0.54%) and CPU variation at 0% to +1.89%. This establishes a useful same-interpreter workload gain, not broad TAR semantics or upstream resource acceptance.

The control and candidate were APFS clones of the same accepted quote-only installed stage. Both received the identical `_tar_checksum_proof.so` and imported it through the identical [runner](tar-checksum-proof/run.py). Only the candidate assigned a wrapper to `tarfile.calc_chksums`: exact built-in `bytes` of length 512 use the Rust scan; every other input uses the saved Python function. The C extension owns the exact bytes argument and returns two Python integers. The `no_std` Rust function sums all 512 bytes except offsets 148–155 as both unsigned `u8` and signed `i8`, starting each sum at 256 for the eight checksum spaces. The compiled extension exports both `_tar_checksum_scan` and `_PyInit__tar_checksum_proof`.

The [probe](tar-checksum-proof/probe.py) matched the installed function's values for zero, high-bit, mixed signed, and changed checksum-field headers, plus its behavior for short/long `bytes`, `bytearray`, `memoryview`, and a `bytes` subclass. The extension itself rejected non-exact headers. No CPython suite was run; this is a bounded checksum proof.

The locked source archive was 44,210,863 bytes with SHA-256 `965dbc9c847b0ed779a16134495b8690c9fc957996d8bcbb83c47089d4e81467`. Every speed and memory attempt read all 6,539 members and streamed 6,031 regular files (136,064,031 bytes) three times. Each attempt produced output SHA-256 `4274d870abacbefea6bbdb2175de8b4073198e1fd39f34ede1c065b3faf1a805`, or 408,192,093 logical regular-file bytes per process. The archive and output digests were checked against the locked input and earlier public-read result. Both cloned interpreters had SHA-256 `622ef6135d157b61254ebbce3778fb424a26d91d1fdc365a66d5fd19ba3797d6`; `tarfile.py`, its valid installed `.pyc`, and the overlaid extension matched byte for byte across arms. Verbose import audits confirmed both loaded the valid `tarfile` cache and extension. Both arms used the same environment, no inherited `PYTHONPATH` or `DYLD_*`, ordinary GC and ASLR, and no sampler during speed measurements.

A separate three-pair memory pass sampled the direct Python child with `ps` while `/usr/bin/time -l` recorded lifetime peaks. Candidate-minus-control median sampled peak RSS was +245,760 bytes (range +32,768 to +573,440); kernel lifetime peak RSS and charged physical footprint each had median −229,376 bytes (range −770,048 to −163,840). The opposing small directions and sparse sampling do not establish a memory change. Each memory attempt had one observed Python PID, 15–16 samples, exact output, and zero swaps. The host swap allocation remained 243.88 MiB before and after.
