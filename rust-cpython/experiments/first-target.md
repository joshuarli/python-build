# First public stdlib experiment: zlib backend

**Selection:** provisionally qualify the already pinned zlib-rs 0.6.7 C ABI beneath the unchanged CPython 3.16 `Modules/zlibmodule.c`. Begin with public decompression through `zlib.decompress`, `gzip`, ZIP member reads, and `zipimport`. Profile representative workloads before implementation; keep the result only if measured application gains exceed noise without material CPU or memory regressions. This is an experiment choice, not a performance claim.

## Evidence and alternatives

| Candidate | Measured reach and result | Compatibility and resource uncertainty |
| --- | --- | --- |
| zlib backend | The isolated overlay exercises public `zlib`, gzip, tar, ZIP, and zipimport paths. Its unchanged CPython tests ran 1,892 cases, with 39 skipped and no failures. The proof verifies a 1,048,589-byte roundtrip and static Rust symbols. No workload throughput or resource comparison exists yet. | Keep `zlibmodule.c` as the Python/C contract. Check streaming, flush modes, dictionaries, checksums, malformed streams, errors, and observable compressed output. Backend allocation and memory behavior are unmeasured. |
| `_base64` bulk path | Direct Rust calls were 39.5% faster at 64 bytes, but 42–48% slower than the existing C/public path from 4 KiB through 16 MiB. Public `Lib/base64.py` still calls `binascii`; the measured smoke Base64 cases invoked `_base64` directly. | Public routing must preserve the pinned 3.16 `padded`, `wrapcol`, and `altchars` behavior. The current Rust function covers only standard encoding. Bulk regression blocks promotion without a new result. |
| `difflib.SequenceMatcher` | Pure Python matching is a plausible coarse kernel, but this repository has no measured application workload reaching it. | Arbitrary sequence elements, `isjunk`, `autojunk`, tie breaking, matching blocks, opcodes, and subclasses make exact compatibility more costly than the zlib backend proof. |

The Base64 timing data are from an M1 Pro macOS 26.5.2 run of the pinned fork at `b812b4a7b9efaca46b98544a8633b7d7e454166b`, with LLVM 23.1.2, ThinLTO, and PGO. See `rust-cpython/PERFORMANCE.md`. The zlib test count and backend identity come from `rust-cpython/results/zlib-proof.json` in the primary checkout and `rust-cpython/zlib-proof/README.md`. Test reach is evidence of compatibility, not measured application time. No measured ranking of zlib against `difflib` exists.

## Experiment contract and decision evidence

Use the current pinned fork with platform zlib as the immediate control for the backend change. Its existing `_base64` module and other build settings must match the zlib-rs candidate. A comparably configured vanilla upstream CPython 3.16 is the primary baseline for CPython improvement and memory parity; the fork built without Rust remains a separate integration control. Record revision, compiler, CPU flags, PGO, LTO, GIL, and input digests; mismatches limit the claim. The zlib-rs source and Cargo lock are already pinned under `rust-cpython/zlib-proof/`; add no dependency or pin for this qualification.

First profile representative startup, packaging, and application work to quantify time spent in codec operations and the public paths that invoke them. Native codec work may dominate an application result, while Python glue may limit it. Report codec throughput and Python glue separately from complete gzip, ZIP, and zipimport workloads; do not infer application benefit from codec throughput alone.

Use deterministic low- and high-compressibility inputs of 64 bytes, 4 KiB, 1 MiB, and 16 MiB. Cover one-shot compression/decompression; streaming in 64-byte, 4-KiB, and 64-KiB chunks; a wheel-shaped ZIP with many small members and larger members; gzip extraction; and cold import from ZIP. Count bytes, members, and imports as logical work units. Include both warm steady work and cold import/startup where relevant.

Run unchanged `test_zlib`, `test_gzip`, `test_tarfile`, `test_zipfile`, `test_zipimport`, and `test_binascii` on control and candidate, plus differential cases for exact decompressed bytes, checksums, dictionaries, flush/copy behavior, malformed and truncated streams, exceptions, and streaming boundaries. Record any compressed-byte differences separately: CPython's `test_zlib.py` explicitly recognizes that valid compression methods may produce different bytes, but those bytes remain observable to callers and require review.

For a quiet-host qualification, collect serial counterbalanced wall timings and kernel-accounted user/system CPU time per logical work unit. In separate passes, collect peak and retained process RSS and private/unique memory, then native and Python allocation counts and bytes. Establish noise with control self-comparisons. The native macOS benchmark harness now has sampled process-tree RSS; unique memory and allocation passes remain open gates. Record installed module and Rust runtime bytes as a separate cost. Reject a clear application time, CPU, or memory regression; retain an unresolved tradeoff as an experiment rather than promoting it. The first exploratory probe is recorded in `zlib-probe-20260924.md`.
