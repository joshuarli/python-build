# Quiet-host zlib ZIP memory comparison (2026-09-24)

**Recommendation: keep the memory question open; do not reject zlib-rs for the earlier ZIP RSS result.** With both interpreters forced to compile Python source from the same cache policy, eight serial `zip_read_wheel` pairs gave a candidate-minus-control median **−147,456 B** root lifetime peak RSS and **−360,448 B** root lifetime peak physical footprint. The paired RSS differences ranged from −4,161,536 to +2,850,816 B. Eight same-session control/control pairs ranged from −2,195,456 to +3,997,696 B. This run does not reproduce the earlier +3.129 MB RSS / +2.916 MB root footprint median. It also cannot establish memory parity under the product gate: source-only startup changes the memory level, native allocation and compatible unique/proportional memory are missing, and host variation remains large. The candidate's differing compressed output in 210/876 samples and +1.59 MB installed extensions remain separate contract/cost issues; this report does not promote the backend.

All 66 successful workload attempts, including every 10 ms sample, kernel peak, process result, checker output, and chronological pair identifier, are in [`data/zlib-quiet-memory-20260924.json`](data/zlib-quiet-memory-20260924.json). That file also preserves the initial failed controller launch and `/usr/bin/time -l` logs. The ignored original attempt files and logs remain in `rust-cpython/results/zlib-quiet-20260924ae/` in this worktree.

All 32 memory attempts exited successfully, reported one observed process, and had zero sampler errors. One control self run and two cross runs had a null footprint *sample* near exit; their kernel lifetime root footprint counters were present. Sampled footprint is a sequential snapshot of Apple's charged dirty memory, not USS/PSS or an exact simultaneous process-tree peak. The workload has no marked retained-memory boundary. The kernel root peaks avoid missed short-lived maxima, but are per-root counters; this ZIP read task had no children.

The five-pair control timing calibration had a median second-minus-first external wall difference of +0.00057 s per four extractions, with range −0.00926 to +0.01587 s. The eight control/candidate timing pairs had median external wall +0.00484 s per four extractions (about +0.00121 s/extraction, median pair ratio 1.024), range −0.00072 to +0.00778 s. The paired total root CPU median was +0.00070 s per four extractions (about +0.00017 s/extraction). The internal extraction timer was −0.00037 s per four extractions; startup/source compilation dominates external wall in this policy. These small, conflicting timing directions do not establish an application speed gain or regression.

An affordable four-pair uninstrumented `zipimport_cold` comparison ran three fresh imports per side per pair. Candidate-minus-control median external wall was +0.00535 s per three imports (range −0.00194 to +0.02205 s); complete root-plus-direct-reaped-child CPU was +0.00338 s per three imports (about +0.00113 s/import). The run did not collect cold ZIP process-tree memory or a same-session cold ZIP timing noise calibration; no cold import performance verdict follows.

The host load average was 3.54/3.26/3.49 before and 3.11/3.19/3.44 after. No concurrent compiler or benchmark was visible in the process check; background OrbStack and system activity remained. End-of-run swap allocation was 243.88 MiB; a start swap allocation was not recorded, so host swap movement is unknown. `/usr/bin/time -l` reported zero swaps for both controller launches and the source-manifest check. It reported **13.10 user + 2.56 system CPU seconds**, 16.94 s elapsed, and 52,723,712 B maximum RSS for the completed controller process tree. The 66 `wait4` workload roots total 14.073599 CPU seconds; the eight cold ZIP runs report another 1.434350 CPU seconds for direct reaped children. These ledgers are near the 15.66 s whole-command CPU total, without treating sampling or short-lived controller overhead as zero. The failed first launch, caused by an absent controller `PYTHONPATH`, used 0.03 user + 0.01 system CPU seconds and 23,232,512 B maximum RSS; it launched no workload. The read-only source-manifest check used 0.16 user + 0.33 system CPU seconds, 22,265,856 B maximum RSS, and zero swaps. Total measured substantial command CPU stayed below 17 seconds, and maximum reported controller RSS stayed below 53 MB, within the 180 CPU-second and 1 GiB limits. No build, dependency change, formatter, linter, hook, or push ran.

The ZIP memory question needs a repeat with the installed bytecode cache state characterized and equalized if production cache behavior matters. Compatible USS/PSS or native allocation evidence would be needed to clear the broader memory gate. The earlier full-candidate timing and code-output concerns remain governed by their own reports.
