# Optional AArch64 NEON Base64 bulk kernel

**Verdict: keep as an optional kernel candidate.** The isolated 48-byte NEON block encoder materially beats both the earlier chunked Rust kernel and staged CPython `binascii.b2a_base64(..., newline=False)` for two large inputs. It has no public route and is not a qualified `_base64` extension result. Public routing remains deferred. If later pursued, a route beneath the existing `binascii.b2a_base64` C API boundary could preserve its argument and option behavior without repeating the rejected extra Python guard, but this experiment does not measure that route.

The [patch](base64-neon-20260925.patch) applies to verified pinned Rust-for-CPython commit `b812b4a7b9efaca46b98544a8633b7d7e454166b`, file `Modules/_base64/src/lib.rs` SHA-256 `3bcc6396bc10c4ae3022b05d7093751428414c0b6c694ee9bace47b725218a17`. Patch SHA-256 is `4b26b291d3b3931d5932b76a70fe4c18360635a5208eb7f653bfceea36521c46`; patched source SHA-256 is `8d059b0b5290d8f3f06b2f84be51db84a54b8e5c686e959d1381c6b5f35b6880`. The patch is not in the manifest. On AArch64, it loads 16 groups of three bytes with `vld3q_u8`, computes four sextet vectors, maps them to the standard ASCII alphabet, and writes 64 interleaved bytes with `vst4q_u8`. The remaining groups and all non-AArch64 builds use the existing chunked scalar scheme. The private function asserts full output capacity before either path, so `zip` cannot silently truncate a valid call. The enclosing module already uses `std`; this adds no dependency, allocator use, or toolchain change.

The [runner](base64-neon-20260925.py) copies the verified pinned source into two isolated scratch trees, applies the prior chunk patch and this patch separately, verifies both changed source identities, extracts the kernel source and adds an identical raw pointer wrapper. Both arms compile as standalone `cdylib` with pinned `rustc 1.100.0-nightly (574ff7d98 2026-09-14)`, `-O -C target-cpu=apple-m1`. The timed run uses the staged pinned Python 3.16 interpreter and its `binascii`; the earlier correctness run used host Python 3.13. Reproduce from the repository root with:

```sh
rust-cpython/stage/bin/python3.16 rust-cpython/experiments/base64-neon-20260925.py \
  --source rust-cpython/work/source-inspect/cpython-b812b4a7b9efaca46b98544a8633b7d7e454166b/Modules/_base64/src/lib.rs \
  --output rust-cpython/experiments/data/base64-neon-20260925.json \
  --scratch rust-cpython/work/base64-neon-20260925 --benchmark
```

The two runs in [compact evidence](data/base64-neon-20260925.json) are `20260925T084135-482ee737` (correctness and compilation) and `20260925T084149-c8f2daab` (same plus timing). Both checked exact output bytes against `binascii` for 18 lengths, three deterministic patterns (SHAKE256, zero, `0xff`), and both Rust arms: 108 checks per run. Lengths span 0–3, both sides of 48- and 96-byte block boundaries, 65 KiB, and 1 MiB, including both padded tail lengths. Each run stores one aggregate identity digest and all failures, if any; there were none. The runner checkpoints each compile, identity sweep, and timed sample by unique ID. The two initial unmetered compiler smoke probes are identified separately in the evidence; their CPU and memory fields were not collected.

| Input bytes | Chunk Rust median | NEON median | C median | NEON/C paired wall ratio |
| --- | ---: | ---: | ---: | ---: |
| 65,538 | 24.35 µs | 8.47 µs | 24.25 µs | 0.352; range 0.345–0.356 |
| 1,048,576 | 389.22 µs | 133.58 µs | 387.34 µs | 0.341; range 0.334–0.358 |

Each arm encoded about 64 MiB per round, seven rounds per size, with rotated and reversed order. At 65,538 bytes, median kernel user/system CPU per call was 24.28/0.06 µs for chunk Rust, 8.43/0.04 for NEON, and 24.08/0.08 for C. At 1 MiB, it was 385.23/3.58, 130.50/3.09, and 383.84/3.83 µs. Wall uses `perf_counter_ns`; CPU uses kernel `getrusage(RUSAGE_SELF)`. NEON same-arm wall ranges were 8.28–8.67 µs and 129.19–137.85 µs. The roughly 65% NEON advantage greatly exceeds those observed ranges, even under the host load. These numbers are a bounded loaded-host diagnostic: an unrelated `xsht` process used about one CPU core during the run, and OrbStack also consumed CPU. They are not quiet-host qualification.

Each Rust arm writes into a reused exact-size output buffer through `ctypes`; C allocates a fresh bytes object. This comparison favors Rust on allocation and excludes `_base64` Python parsing, allocation, and any public route. The comparison covers only contiguous input and standard padded, unwrapped output. It does not establish alternate alphabets, wrapping, buffer variants, monkey-patched `binascii`, or whole interpreter performance.

For the timed run, direct chunk compilation took 0.192 s wall, 0.125 s user, 0.081 s system, with 103.6 MB peak RSS; NEON took 0.217 s wall, 0.154 s user, 0.084 s system, with 113.9 MB peak RSS. `/usr/bin/time -l` covered each compiler process tree; `getrusage(RUSAGE_CHILDREN)` supplied CPU. The runner process peaked at 47.5 MB RSS; that shared process peak cannot attribute memory to a single arm. Host swap stayed at 243.88 MiB, with zero process swaps in compiler time output. `size -m` reported 207,228 bytes of Mach-O `__text` for chunk Rust and 207,804 for NEON, a 576-byte increase; both dylibs were 422,624 bytes. No full CPython build, test suite, formatter, linter, hook, commit, or push ran in this lane.
