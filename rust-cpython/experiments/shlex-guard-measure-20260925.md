# Guarded `shlex.split` complete-task measurement

**Verdict: retain the current 0009 guard as an opt-in performance candidate, with a quiet-host timing gate still open.** This is a bounded diagnostic because background load persisted. On the deterministic 25,264-call public `shlex.split` command-processing task, five counterbalanced complete-process pairs gave a median guarded/pure kernel user-plus-system CPU ratio of **0.369** (range 0.364–0.372). The median wall ratio was **0.380** (range 0.377–0.384). Every run produced the expected digest `f3044038f323d044f07ff99da59314f8861473624726d4483aeb1b9cea1f4afe`, with 163,580 tokens and 632 expected parse errors. These are results for the current binding-guard revision, not the earlier pre-guard candidate.

The same read-only accepted CPython 3.16 executable (`6eeeb64b…e3c9531bd`) ran both arms. The pure arm used its pinned `shlex.py` (`3e75f98d…eb24150`). The guarded arm applied the current 0009 parser hunk to those same source bytes and matched the selected guarded source hash `10afd968…65c1d24a96e1`. The 0009 patch hash was `de3ae626…baf`. Its exact new C and Rust source hunks were extracted into this worktree and built as a standalone private extension with pinned nightly `2026-09-15` Rust and locked LLVM 23.1.2 clang. The extension hash was `497a9046…e7b9b331ab`, 50,936 bytes. Static symbol inspection found `PyInit__rust_shlex_split` and `shlex_split_scan`, no unresolved Rust personality symbol, and only `libSystem` as a dynamic dependency. This extension is a direct standalone build from the patch source; it is not a full CPython build artifact.

Each child ran the existing `shlex_split_workload.py --count 12000 --rounds 2` with the same interpreter, `-S -B`, `PYTHONDONTWRITEBYTECODE=1`, fixed `PYTHONHASHSEED=1`, and an empty `PYTHONPYCACHEPREFIX`. `PYTHONPATH` selected the arm's source overlay; both arms compiled their source with no bytecode cache. Direct parent `wait4` supplied child user/system CPU, lifetime maximum RSS, and swaps; parent `perf_counter` supplied wall time. Two control/control and two guarded/guarded pairs preceded the five alternating-order comparison pairs. Their wall self-ratio ranges were 0.959–1.001 and 0.977–0.981; CPU self-ratio ranges were 0.985–1.006 and 0.980–0.986. Every timing child reported zero swaps. [Raw observations and exact recipe](data/shlex-guard-measure-20260925.json) retain every attempt and the host samples.

A separate three-pair `/usr/bin/time -l -p` pass checked the same complete output and measured peak physical footprint. Guarded-minus-pure footprint differences were **+180,248, +737,280, and +933,864 bytes** (median +737,280 bytes); all six children reported zero swaps. This is a small positive observed process peak with only three pairs and no same-side footprint calibration. It does not establish unique or proportional memory growth or allocation counts.

The successful standalone build took **0.397 s wall**, **0.173 s user CPU**, **0.114 s system CPU**, and reached **98,287,616 bytes** maximum per-process RSS, with zero swaps. An initial build attempt compiled Rust but failed when clang could not find `assert.h`; adding the active Xcode 26.5 SDK sysroot resolved it. Both attempts, including CPU, RSS, swaps, and the failure, are retained in the raw data. Build cost here measures only the standalone extension, not a full PGO interpreter build.

Host load averaged about 2.7–3.4 on ten logical CPUs during the successful measurements, with OrbStack typically sampling at roughly 12–22% CPU before pairs; an earlier failed build sample reached 197%. The counterbalanced CPU separation substantially exceeds both same-side CPU ranges, but these loaded-host numbers are not a publishable speed claim. Wall and footprint remain provisional. No full PGO build, CPython test suite, formatter, linter, hook, dependency change, or product change ran. Broader behavior and Linux qualification remain separate decisions.
