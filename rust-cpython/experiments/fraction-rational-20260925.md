# Canonical `fractions.Fraction` rational text experiment

**Verdict: retain the opt-in scanner for partial public `fractions.Fraction` parsing coverage.** The complete ledger output matches the control, and the optional native route is installed. The loaded-host comparisons below are diagnostics only. They do not establish a clean-host speed gain or memory parity; both require requalification after the unrelated container work ends.

The complete workload builds a deterministic 16-account ledger through public `Fraction` calls, adds each parsed amount to its account, formats the totals, and hashes the rendered account summary. Four of every 20 entries use fallback-oriented templates: padded rational text, decimal text, underscored integer text, and integer text. The other 16 use exact ASCII `[-]?[0-9]+/[0-9]+` text. For small magnitudes, the underscore template emits no underscore, so a few of those records also reach the fast route. The output field `canonical_records` counts the 16 canonical templates per 20 rows; the candidate profile observed 32,036 scanner successes out of 40,000 calls. The timing recipe processes 100,000 entries twice; the route profile used 20,000 entries twice. The profile's complete output digest was `223d04b46a99a5f27cf9adbd0c7afa74f10c72f7d1576c55f0162c7655dcc985`.

On the read-only `stage-shlex-split` control, `cProfile` recorded 0.236880291 s for the 40,000-record task. Regex `match` used 0.016023384 s self time and match `group` used 0.014539078 s; these nonoverlapping calls totaled 12.9% of the instrumented task. The 80% eligible row share makes the directly replaceable headroom near the 10% gate. The `Fraction.__new__` cumulative time was 0.109395024 s, but includes allocation and normalization that remain in Python and was not added to the gate. Instrumented time is only a route diagnostic.

A candidate `cProfile` of the same 40,000-record task under external host load matched the digest and recorded 0.228188292 s total. Regex `match` and match `group` fell to 0.004367587 and 0.003986538 s self time, while the Rust scanner accounted for 0.004235961 s across 40,000 calls. `Fraction.__new__` self time fell only from 0.060400455 to 0.054290548 s; the repeated import opcode and Python guard remain within that frame. The profiler recorded six actual `builtins.__import__` calls, so repeated library import work is not established. These instrumented observations show route displacement and remaining Python overhead, not a publishable speed ratio.

`0010-rust-fraction-rational.patch` adds an opt-in `--fraction-rational` build selection. The fast route requires the exact `Fraction` class, exact ASCII `str`, default denominator, original regex and `int` bindings, and canonical rational syntax. Each integer has at most 18 digits, the denominator is nonzero, and the full input is at most 38 bytes. A private no_std Rust scanner returns two integers. Python still constructs the `Fraction`, normalizes with `gcd`, and handles all fallback inputs and errors. This covers only a narrow public parsing path; broader semantic and instrumentation effects remain unqualified.

Fresh verified source extraction, application, and reverse checks passed for default, fraction-only, candidate stack, and all-optional selections, changing 8, 11, 20, and 26 intended paths respectively. The candidate stack is `--strptime-numeric --uuid-canonical --shlex-split --fraction-rational`, based on the same pinned Rust-for-CPython commit and locked LLVM, nightly Rust, ThinLTO, `-O3`, and native CPython PGO recipe as the control. The first candidate build failed at install: the extension import had unresolved `_rust_eh_personality`; checked slice access removed it. The successful full rebuild took 300.80 s wall, 703.76 s user CPU, 114.30 s system CPU, peaked at 1,757,921,280 bytes RSS, and reported zero swaps. Build wall time overlapped other host activity. Installed and patched-source `fractions.py` both hash to `f493e8a7cb4af622534e6e2b4fcfc0dd4af711c3ad63cf9c09c05e2c028c9d7c`; the extension exports the scanner and has no unresolved Rust unwind personality.

The private installed extension is 51,168 bytes. Under the existing `.so`/`.dylib`/`python3.16*` native-file rule, aggregate installed size rises from 17,180,769 to 17,224,798 bytes (+44,029), including variation in separately profiled native outputs.

An explicitly nonpublication calibration ran six control processes while an unrelated OrbStack container used several CPU cores. All six produced the same 200,000-record digest, `356356bd5c02a8e41cfb64a19ec168f35a6a752ed9c5e1c7b3b15b2635d284e9`. Three second/first control wall ratios were 0.99273, 0.99631, and 1.01073; the corresponding kernel CPU ratios were 1.01786, 1.00000, and 1.01786 at 0.01-second resolution. Peak RSS ranged from 44,400,640 to 45,137,920 bytes, with zero process swaps. These control results establish short local consistency under load, not a candidate speed claim.

One further nonpublication pair under the same external load produced matching digests and candidate/control ratios of 0.8875 wall and 0.9123 kernel CPU. Peak RSS changed from 43,991,040 to 45,187,072 bytes and peak footprint from 31,359,480 to 32,522,744 bytes, with zero swaps. The pair is a route diagnostic only; it cannot establish performance or memory acceptance.

With the external container still active, a second nonpublication pass ran three nearby control/control pairs and five alternating control/candidate pairs. All 16 processes matched the 200,000-record digest and reported zero swaps. The second/first control wall ratios were 0.9373, 0.9944, and 1.0051; the first self pair therefore had 6.3% drift under load. Control CPU ratios were 0.9825, 1.0000, and 1.0000. Median candidate/control ratios were 0.9272 wall (range 0.9180–0.9858) and 0.9286 kernel CPU (range 0.9107–0.9464). Median paired peak RSS and footprint changes were -98,304 and -131,072 bytes, within the self-pair RSS drift of -16,384 to +770,048 bytes. Host load averaged 10.22 before and 9.80 after this pass, with unchanged host swap usage. The apparent gain is directionally useful, but the control drift and concurrent container load prevent a performance promotion or memory acceptance claim.
