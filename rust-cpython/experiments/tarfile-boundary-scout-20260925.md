# Tarfile header boundary scout, 2026-09-25

**Verdict: consider only a checksum-scan proof; defer a Rust header, PAX, or extraction parser.** The real locked CPython source archive has measurable header work, but the present profile does not show a safe, coarse replacement for `TarInfo._frombuf`. Its 141.27–141.29 ms cumulative control time is a subtree, not exclusive Python time. The smallest promising boundary is `calc_chksums`: 43.23–43.27 ms cumulative across 6,540 complete headers in an instrumented 581.42–581.52 ms read. That is a 7.4% instrumented ceiling if the whole checksum call vanished, not a speed forecast. A native scan would still pay a call and object-construction cost. No candidate, build, semantic test, or speed measurement was run here.

## Evidence and disjoint cost

The existing [source-tar attribution](source-tar-attribution-20260925.md) profiled one checked `tarfile.open(path, mode="r:gz")` read per process on the accepted fork control twice and zlib hybrid twice. The [workload](source_tar_hybrid.py) visits 6,539 members, hashes 136,064,031 regular-file bytes across 6,031 files, and produces digest `4274d870abacbefea6bbdb2175de8b4073198e1fd39f34ede1c065b3faf1a805`. Its 44,210,863-byte locked archive has SHA-256 `965dbc9c847b0ed779a16134495b8690c9fc957996d8bcbb83c47089d4e81467`. I reused the existing [raw function rows](data/source-tar-attribution-20260925.json), with no new cProfile run. The control and hybrid installed `Lib/tarfile.py` sources have the same SHA-256 `a1a9f6ed36eb63b24a1bfb2c70210c2f42251559e796968183e90202b34bd44a`; I inspected that read-only installed source under the control worktree. Its source pin is Rust-for-CPython commit `b812b4a7b9efaca46b98544a8633b7d7e454166b`.

The 141 ms `_frombuf` subtree includes `nti`, `nts`, and `calc_chksums`. Their cumulative values cannot be added to it or each other. The `nti` and `nts` self rows are disjoint, but `nts` aggregates numeric and ordinary text fields; the retained profile has no caller edge data to time those two groups separately. PAX framing and decoding occur only once, so this archive cannot establish a useful PAX optimization target. The separate `TarInfo._proc_builtin` cumulative 30.6–30.7 ms includes `_apply_pax_info` and other member processing; it is outside `_frombuf` but cannot be credited to header parsing alone. Content-wrapper `readinto` and `read` self rows account for another 21.9 ms of the `tarfile.py` self sum and are unrelated to the proposed header scan. The zlib hybrid's extra time was already localized to `zlib._ZlibDecompressor.decompress`, so this header work does not explain that regression.

## Narrow possible boundary

Keep `TarFile.next`, file-like reads, stream offsets, `TarInfo` construction, `_frombuf`, `_proc_member`, PAX/global headers, GNU sparse and long-name processing, extraction filters, and error translation in the existing Python path. A private Rust helper could scan one exact built-in `bytes` object of length 512 for both unsigned and signed checksums, treating the eight checksum bytes as spaces, and return the same pair of Python integers. Dispatch only from the existing `calc_chksums(buf)` helper for `type(buf) is bytes and len(buf) == 512`; retain its present `struct.unpack_from` and `sum` behavior for other buffer-compatible objects and lengths. This preserves the public `tarfile` entry path, header validation order, malformed-header exceptions, custom file-like objects, streaming, and existing calls to overridden `TarInfo` methods. It also leaves numeric octal/base-256 variants, name decoding and error handlers, PAX/global semantics, mutable or subclassed `TarInfo`, filter callbacks, and path security in Python. The helper's global lookup remains available for callers that replace it.

A proof must first compare exact checksum return values and exceptions against the original helper for normal, signed-high-bit, malformed, non-512-byte, and buffer-protocol inputs; then use unchanged `test_tarfile` behavior and malicious archive fixtures. Timing must use uninstrumented, cache-matched public archive reads with control self-calibration and process CPU, wall, memory, and allocation evidence. If that complete workload fails to improve beyond noise, stop; the remaining parse functions have smaller exclusive slices and much wider semantic surfaces. A full native header/PAX parser should wait for a workload with more exclusive parsing time or a stronger validated contract boundary.
