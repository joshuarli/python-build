# Static feasibility: one-shot Rust inflate, platform streaming inflate

**Recommendation: a small, isolated candidate is feasible, but the present hybrid must not be promoted.** Keep prefixed zlib-rs only for public `zlib.decompress(data, wbits, bufsize)` and return both streaming decompressor types to platform libz. This is a routing experiment, not evidence that the source-tar regression disappears or that the resulting binary meets size and memory gates. No source was changed or executed for this review.

## Source and ABI boundary

The current optional patch, `patches/0002-zlib-hybrid-inflate.patch`, puts preprocessor aliases near the top of pinned `Modules/zlibmodule.c`. Under `PYTHON_BUILD_ZLIB_HYBRID`, every `inflateInit2_`, `inflate`, `inflateEnd`, `inflateCopy`, and `inflateSetDictionary` call resolves to a `python_build_rs_` symbol. This covers the local `z_stream` in `zlib_decompress_impl` and the persistent streams in `zlib_decompressobj_impl`/`zlib.Decompress` and private `zlib._ZlibDecompressor`. The build recipe already links both backends into the same extension: `rust-cpython/build.py` sets `ZLIB_LIBS` to `-lz <prefixed Rust archive>`, enables the guard in `CFLAGS`, and checks that the archive has prefixed entry points without unprefixed zlib exports. Platform `zlibVersion`, deflate, and checksums provide the public version identity and compressed bytes. `binascii` is separately restored to `-lz` in the generated Makefile.

The narrow candidate should remove the file-wide inflate aliases. In `zlib_decompress_impl` alone, call `python_build_rs_inflateInit2_(&zst, wbits, ZLIB_VERSION, sizeof(z_stream))`, `python_build_rs_inflate(&zst, flush)`, and `python_build_rs_inflateEnd(&zst)` at **every** success and error exit after initialization. Keep the prefixed prototypes under the candidate guard; use the ordinary platform calls when the guard is absent. The explicit init call has the same C ABI arguments as zlib's `inflateInit2` macro, which expands to `inflateInit2_` with the header version and `sizeof(z_stream)`. The existing hybrid already passes those values to the Rust ABI; this proposal changes which streams use that ABI, not their layout. An equivalent tightly scoped wrapper is possible, but file-wide macros are too broad for this split.

Leave `set_inflate_zdict`, `zlib_decompressobj_impl`, `Decomp_dealloc`, `zlib_Decompress_decompress_impl`, `zlib_Decompress_copy_impl`, `zlib_Decompress_flush_impl`, and the private `_ZlibDecompressor` initialization, dictionary, decode, and teardown paths on **unprefixed platform** `inflate*`. A copied stream must stay on its creator's backend. The one-shot stream has no copy or dictionary operation; all its calls can remain Rust from init through end. No inflater state crosses the boundary. `zlib.compress`, `compressobj`, Adler/CRC, and `zlibVersion` stay platform, preserving the current compressed-byte policy and the platform `ZLIB_RUNTIME_VERSION` (currently asserted as `1.2.12` in the hybrid recipe). The public version must not be relabeled as the Rust backend, nor may the apparent platform version conceal changed compression output.

`gzip.GzipFile` constructs private `zlib._ZlibDecompressor`; `gzip.decompress` constructs `zlib.decompressobj`; `tarfile.open(..., "r:gz")` reads via `gzip.GzipFile`, and `tarfile` stream mode `r|gz` constructs `zlib.decompressobj`. All therefore use platform inflate in the proposed split. This directly removes Rust inflate from the source-tar workload's streaming path. It also removes Rust from gzip workloads using those APIs, including any sustained `gzip_extract_1m` task that uses `gzip.GzipFile` or `gzip.decompress`; the earlier approximately 36% gzip gain cannot be carried forward by assumption. Public one-shot `zlib.decompress` remains the only Rust decode entry point and is the path relevant to the sustained `zlib_decode_1m` result.

## Recipe, symbols, and size

A new optional candidate mode or a clearly renamed replacement for `--zlib-hybrid` should select a revised source patch and record the routing in build provenance. The current `--zlib-hybrid` mode does **not** implement this split. The patch manifest digest must change with the patch. Preserve the existing pinned zlib-rs source, `custom-prefix` feature, `LIBZ_RS_SYS_PREFIX=python_build_rs_`, `-lz <archive>` module link, and platform-only `binascii` link. Update the installed-module report so it verifies references or relocations to both prefixed Rust one-shot symbols and unprefixed platform inflate symbols, `/usr/lib/libz.1.dylib`, no unprefixed zlib definitions in the extension, and unchanged platform version identity. The existing archive-symbol check proves only that the prefixed archive defines entry points; it does not prove the final module routes streaming calls correctly. A source-level call-site audit plus installed-symbol inspection is needed.

The existing hybrid made the installed zlib extension 1,592,928 bytes larger unstripped and 1,451,456 bytes larger after the equal debug-strip diagnostic than the control. The split still links Rust inflate code and platform libz, so it cannot be expected to erase that cost. Dead-code stripping might drop Rust copy/dictionary paths once no longer referenced, but archive object granularity and Rust reachability determine whether it does; there is no measured size for this proposal. Repeat equal-policy stripped and unstripped sizes and the product package-size gate before promotion.

## Required evidence for a built candidate

1. Verify every intended `Modules/zlibmodule.c` call site in a freshly extracted tree, patch manifest hash, configured `ZLIB_LIBS`, generated module and `binascii` link flags, final load commands and defined/undefined symbols. Run a runtime identity check for `ZLIB_VERSION`, `ZLIB_RUNTIME_VERSION`, extension path, and `binascii` platform dependency. A whole-module round trip alone cannot distinguish the split.
2. Exercise one-shot zlib and raw/gzip `wbits`, truncated/corrupt inputs, zero and small output buffers, and exact decoded bytes/errors. Exercise public streaming `decompressobj` across chunk boundaries, `max_length`, `flush`, `unused_data`, `unconsumed_tail`, EOF, preset dictionaries, and `copy` before and after input. Exercise private `_ZlibDecompressor`, gzip concatenated members, CRC/trailer errors, `gzip.GzipFile`, `gzip.decompress`, `tarfile` `r:gz` and `r|gz`, and ZIP reads. Check compressed-byte compatibility on platform compression paths.
3. Re-run paired control/candidate complete-process wall and kernel CPU for the locked source-tar digest workload, sustained `zlib_decode_1m`, and sustained `gzip_extract_1m`, plus at least one chunked public `decompressobj` consumer and gzip/tarfile application read. Keep matching source/cache policy and output digests; measure memory and stripped size separately. The prior source-tar result was +11.67% wall and +10.81% CPU for the all-Rust-inflate hybrid. The [attribution profile](source-tar-attribution-20260925.md) found 1,178 decompressor C method calls per source archive and about 41 ms hybrid extra self time; this explains why routing per-call streaming work matters, but it does not measure the proposed split. Reject if the source-tar regression persists or the retained one-shot gain does not justify size and breadth costs.

This assessment used the existing patch, pinned CPython source wrapper and standard-library callers, build recipe, and the sustained and source-tar reports only. It ran no build, compiler, test, benchmark, or profiler and makes no CPU or memory resource claim.
