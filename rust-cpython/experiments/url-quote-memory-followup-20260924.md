# Guarded URL quote request-path memory and cold-import follow-up

## Verdict

The earlier **+0.25–0.49 MB request-path peak-RSS direction did not repeat** in this ten-pair follow-up. With byte-identical child checker code, the candidate minus prior accepted fork median was **−8,192 bytes** (−147,456 to +311,296 bytes); both control/control and candidate/candidate spreads covered every candidate/control difference. The sampled footprint median was −65,524 bytes and was likewise inside same-side spreads. This is no evidence of a repeatable request-path RSS regression, but it cannot qualify unique or proportional memory or allocations.

Cold `import urllib.parse` incurred a **small repeatable process CPU cost** on this host. In the final five counterbalanced rounds of 20 fresh processes per arm, the candidate/control summed `wait4` user-plus-system CPU ratios were **1.037, 1.020, 1.009, 1.017, 1.025** (median **1.020**). Same-side CPU ratios spanned 0.992–1.009 for control and 0.990–1.012 for candidate. The median per-process CPU was 23.508 ms control versus 24.102 ms candidate, about **+0.594 ms** for the complete fresh-process sentinel. The lowest round overlaps candidate self-noise; the five-round median exceeds both self ranges. Two preceding runs with variant-specific checker literals had CPU medians 1.027 and 1.026, consistent in direction but retained as diagnostics.

The final import wall ratios were 1.071, 1.055, 1.026, 1.050, and 1.073. One candidate/candidate self round reached **1.643**, so wall latency is **inconclusive** under local interference. Import peak RSS had a +180,224-byte paired median across ten pairs, within its control self range (−311,296 to +196,608 bytes) and close to the candidate self range (−212,992 to +147,456 bytes). Its sampled footprint saw only 3–5 points in the short-lived children and varied by several MB, so it cannot resolve import memory.

## Discarded diagnostics and host noise

The first follow-up path pass gave a +73,728-byte median and nine positive, one zero candidate/control differences. Its checker embedded variant-specific absolute prefix and parser literals; only the candidate embedded a nonempty extension path literal. That changed command length, code-object size, and identity-check work before the path task. The final checker made the command text identical and its median became −8,192 bytes with mixed signs. The checker difference is a **likely confounder**, not an isolated causal attribution. The earlier breadth report's +0.25–0.49 MB direction and this follow-up's first pass should not be treated as a reproduced memory regression. All discarded rows remain under `*-asymmetric*` keys in the raw JSON.

Two earlier 600-process import timing passes with the asymmetric checker had candidate/control CPU medians 1.027 and 1.026. Their wall medians were 1.085 and 1.072; one control/control round was 1.079. The final byte-identical checker pass also had unstable wall: candidate/candidate round zero was 1.643 while its CPU ratio was 0.990. A separate cargo/rustc job began at approximately 17:25:21 as the final path pass ended; it cleared before the final import timing. Other desktop activity and 243.88 MiB of system swap remained present. No direct evidence attributes the final wall outlier to a particular process. At the agreed roughly 200 CPU-second lane budget, I stopped measurement rather than select a favorable wall run.

Short inspections and later preflights were also not timed. These omissions do not change the reported measured-pass totals, but the 185.47-second figure is not a whole-lane CPU total.

The path RSS signal is inconclusive at this scale and does not justify rejecting the guarded patch on observed peak RSS. Compatible macOS USS/PSS and native/Python allocation evidence is still unavailable, so upstream resource parity remains open. No production source, build driver, benchmark harness, dependency, or workload definition changed in this lane.
