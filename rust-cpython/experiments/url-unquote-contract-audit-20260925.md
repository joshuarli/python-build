# URL unquote proof: static contract audit, 2026-09-25

## Scope and source identity

This is a read-only inspection of `url-unquote-proof/{build.py,module.c,quote.rs}` and the accepted installed CPython 3.16 `Lib/urllib/parse.py`. The parser SHA-256 is `85ac4db38a30e3b12dd78ff0a5b83baa61caedebc3a44c33cd45c85c3279acee`, matching `build.py`'s pinned anchor. No candidate was run, built, or modified for this audit.

`build.py` inserts its guard after public `unquote`'s bytes branch, no-percent return, and `None` normalization. Only exact `str` input, exact `str` codec and error names with values `utf-8` and `replace`, and ASCII storage enter the native decoder. Non-ASCII text falls back through `NotImplemented`. `unquote_plus` first calls `replace('+', ' ')`; string `parse_qsl` calls `unquote_plus` for retained fields. Bytes `parse_qsl` uses `unquote_to_bytes`, outside the route.

## Findings, ranked

1. **Medium: observable lazy state differs.** For an eligible input such as `'%41'`, accepted `unquote` enters `_unquote_impl`, which initializes the module global `_hextobyte` if it is `None`. The guarded route returns before this happens. The returned text is still `'A'`, but introspection of `urllib.parse._hextobyte` and subsequent code that mutates that mapping can distinguish the paths. An already initialized or monkeypatched `_hextobyte` is bypassed too: a changed mapping can alter accepted `unquote('%41')` while native decoding still returns `'A'`. This is a concrete change to private but reachable state and monkeypatch behavior, not an ordinary URL result mismatch. Decide explicitly whether preservation is required before promotion; if it is, the route needs a narrower eligibility rule or compatible state handling.
2. **Low: other replaceable parser internals are bypassed.** Eligible calls no longer consult `_asciire`, `_generate_unquoted_parts`, or `_unquote_impl`. Rebinding these globals can change accepted results, raise exceptions, or count calls; the native route ignores them. Standard library internals are private, so this may be an accepted boundary, but the behavior should be stated in the source change review. The new `_rust_url_quote.unquote_ascii` lookup is itself mutable and can introduce a different interception point.
3. **Low, pending dynamic evidence: codec dispatch identity.** The accepted path calls `bytearray.decode(encoding, errors)` for an escaped ASCII run; the C route directly calls `PyUnicode_DecodeUTF8(..., "replace")`. Their normal UTF-8 replacement results should match. Whether codec registry modifications under the exact canonical name can distinguish the two paths is not established by static inspection. This needs a focused check if custom registry behavior is in scope. Nondefault names, aliases, subclasses, and custom error names stay on the accepted path; `None` normalizes to the defaults before the guard.

No direct memory safety defect was found in the exact guarded route. The input is an exact, ready ASCII Unicode object; `PyUnicode_1BYTE_DATA` supplies `len` bytes. C allocates a `len`-byte output object and Rust writes at most one byte per consumed input byte, checking capacity before each write. Rust's index additions occur only after `input_len - read >= 3`, and `read` never exceeds `input_len`. Both lengths come from `Py_ssize_t`, so the `isize::MAX` check and pointer offsets are bounded by live CPython object sizes. C checks the returned length, releases the buffer on every return path, and passes an explicit length to UTF-8 decoding, preserving embedded NUL. The module has no C or Rust mutable globals, and its multiphase definition declares per-interpreter GIL support; the Python parser state remains per interpreter. These conclusions depend on the CPython C API buffer and Unicode invariants and do not prove compiled behavior or ABI integration.

## Semantic reasoning and qualification before a source build

For exact ASCII input, the accepted generator has one ASCII match and no literal non-ASCII segment. `_unquote_impl` splits at every `%`, converts only two following ASCII hex digits, and otherwise retains `%` and the following bytes. The Rust loop makes the same single-pass decisions, including incomplete escapes, overlapping percent signs, and escaped percent signs that must not be decoded a second time. Adjacent decoded invalid UTF-8 bytes remain adjacent before one replacement decode, so a single decode of the entire Rust output should match the accepted single run. The public no-percent return remains before the guard, preserving object identity there. `str` subclasses and objects with overridden `__contains__`, `split`, or `replace` do not enter the helper unless earlier public operations produce a new exact string. `parse_qsl` field selection, limits, and error handling precede this route and retain their order.

Before spending a full source build, use a small isolated differential harness against the pinned interpreter for returned values, result types and identities, exception type/message, and relevant module state. Cover every byte value through `%HH`, adjacent invalid UTF-8 sequences, malformed and repeated `%`, escaped and literal NUL, long inputs around allocation pressure, ASCII versus mixed non-ASCII text, no-percent returns, subclasses, bytes/bytearray, `None` and custom codec/error arguments, `unquote_plus`, and retained/ignored `parse_qsl` fields. Include monkeypatched `_hextobyte`, `_unquote_impl`, `_generate_unquoted_parts`, and `_asciire` if their private behavior is intended to remain observable. Exercise the native module in a subinterpreter and verify independent parser state. Validate the candidate parser source and checked-hash cache identities before any measured or comparative run. Full `test_urlparse`/`test_urllib` and installed-tree checks belong after a promoted source build.
