# POSIX `shlex.split` scanner experiment

**Verdict: keep the guarded opt-in as a performance candidate for repeated command parsing.** Five serial complete-process pairs gave a median candidate/control wall ratio of **0.363** and kernel user-plus-system CPU ratio of **0.328**. The corresponding reductions were 63.7% wall and 67.2% CPU for this task. Three in-run control/control pairs had median wall ratio 1.006 (range 1.000–1.012); six earlier calibration processes took 0.6000–0.6322 s, with the first process highest. Every process produced digest `f3044038f323d044f07ff99da59314f8861473624726d4483aeb1b9cea1f4afe`. Raw process observations, failures, and recipes are in [compact evidence](data/shlex-split-20260925.json).

The deterministic workload processes 12,632 shell-like command records twice. It splits 24,000 ordinary command records through public `shlex.split`, aggregates token counts and command buckets, and hashes serialized tokens. The records cover build flags, quoted spaces, adjacent quotes, escaped whitespace and backslashes, empty tokens, literal newlines, shell punctuation, and non-ASCII paths. Another 1,264 calls exercise `comments=True`, non-POSIX mode, and malformed quote or escape fallback. The complete output has 163,580 tokens and 632 expected parse errors. On the read-only control stage, `cProfile` attributed 1.077 of 1.232 instrumented complete-task seconds (87.4%) to `shlex.split`, including 0.924 s in `read_token`. The initial profile attempt completed the task but could not save stats until its output directory existed; the rerun succeeded. Instrumented time is a route gate, not speed evidence.

`0009-rust-shlex-split.patch` keeps public `split(s, comments=False, posix=True)` and the original `shlex` class. Its private no_std Rust scanner handles exact ASCII `str` of at most **4,096 characters** under the exact default options while the original class binding and core methods remain unchanged. The C boundary builds the public token list. Non-ASCII strings, longer inputs, malformed quote or escape syntax, subclasses or changed core parser hooks, and alternate options use the existing Python parser. The length cap bounds temporary token-length storage to about 32 KiB per call. This is partial coverage: source stacking, punctuation mode, custom streams, and non-POSIX behavior stay in Python. The complete-task digest is the only behavioral comparison run; semantic probes and CPython tests were excluded by the experiment brief. Broader semantic and Linux qualification remain open.

The control is the prior canonical UUID stage from the same pinned Rust-for-CPython commit `b812b4a7b9efaca46b98544a8633b7d7e454166b`, with default patches, `--strptime-numeric`, and `--uuid-canonical`. The candidate adds `--shlex-split` with `--variant shlex-split`. Both use the locked LLVM 23.1.2, ThinLTO, `-O3`, Apple M1 baseline, native PGO task `-m test --pgo -j 9`, and pinned Rust nightly `2026-09-15`. Fresh source checks changed exactly 8 intended paths for default, 11 for shlex only, 17 for the candidate stack, and 23 for all optional modes, with reverse checks. Several draft patch orders failed where other optional modules inserted beside the URL module; the final patch uses a stable single-line anchor and the builder enables `git apply --unidiff-zero` only for that patch. All failures are summarized in the evidence. Installed `shlex.py` SHA-256 equals the final patched source SHA-256, `7775524252ef7660a73b8be8b2c5995d74df50f82ad7ff7a4f1abca2ac8196af`; the installed extension exports its Rust scanner and has no unresolved Rust personality symbol.

The one full candidate build succeeded in **274.82 s wall, 699.07 s user CPU, 108.40 s system CPU**, with maximum process RSS 1,767,178,240 bytes and zero process swaps. An unrelated `xsh` Rust compile began during this build, so its wall cost is contaminated; it had ended before calibration and published pairs. The private extension is **51,416 bytes**. Under the same `.so`/`.dylib`/`python3.16*` file rule, aggregate installed native size increased **63,282 bytes** (17,117,487 to 17,180,769), which includes PGO variation in other outputs.

Median paired peak RSS and footprint changes were each **+262,144 bytes**. Candidate RSS differences ranged from -327,680 to +573,440 bytes, inside the 409,600–622,592 byte drift seen in the control/control pairs; no material peak-memory regression is established. All timing processes reported zero swaps. Five cold `import shlex` pairs had median wall ratio 0.935 with kernel CPU tied at 0.01 s resolution and median RSS change +49,152 bytes; these do not establish an import-speed change. Unique or proportional memory and allocator counts were unavailable. Timing used `/usr/bin/time -l -p` for Darwin kernel CPU, peak RSS, footprint, and swaps, plus a parent `perf_counter` wall clock. Both sides used `-B`, `PYTHONDONTWRITEBYTECODE=1`, and an empty `PYTHONPYCACHEPREFIX` so each fresh process compiled installed source instead of reading a mismatched bytecode cache.
